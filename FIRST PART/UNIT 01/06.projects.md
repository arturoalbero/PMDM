# Projects with Flutter

To create a new project with Flutter, we'll use the `flutter create` command, which supports some additional options. Additionally, both VSCode and Android Studio allow project creation from their interface, as we'll see further on.

But before tackling project creation in a practical way, let's look at what the structure of a Flutter project looks like.

## Structure of a Flutter Project

A typical Flutter project consists of the following most important directories and files:

**lib directory:** Contains the Dart source code of our Flutter application, which will be compiled into platform-specific code. The main file is `main.dart`, which is the entry point of the application.

> **Dart Projects**
>
> When we generate a pure Dart project, to be run from the command line, the main code is located in the `bin` directory, while `lib` is used for libraries.

**pubspec.yaml file:** Project configuration file in YAML format, where library dependencies and resources (images, fonts, audio, etc.) are mainly defined.

Additionally, we have directories for each platform the project supports:

**android directory:** Contains the Android project, including the Gradle configuration and other native files such as `AndroidManifest.xml`.

**ios directory:** Contains the iOS project, which will require Xcode to work with it.

**web directory:** Contains the HTML and JavaScript files for the web application.

There may also be directories for other platforms, such as `linux`, `windows`, etc., with the native code for that platform.

Other files we might also find in the project include:

- **.gitignore:** Configuration to prevent certain files from being versioned.
- **.metadata:** Hidden file for tracking the project's state.
- **analysis_options.yaml:** Contains the code analysis configuration to display Dart code warnings.
- **README.md:** File in Markdown format to describe the project.
- **pubspec.lock:** File containing information about the installed dependencies.

## Creating and Running a Project in VSCode

Let's see how to create and launch a Flutter project from VSCode.

### Step 1. Creating the project from VSCode

To create a Flutter project in VSCode, we open the Command Palette with `Ctrl+Shift+P` and select **Flutter: New Project**.

If VSCode doesn't detect the Flutter SDK, we'll be asked to indicate the correct path for the Flutter SDK and the Dart plugin.

Once the SDK is configured, the wizard will ask us to select the type of Flutter application to create and the destination directory.

When the wizard finishes, a command similar to the following will be run:

```
flutter create --template app --ios-language swift --android-language kotlin .
```

This specifies the project type (app), and the default languages to be used natively on iOS and Android.

### Step 2. Checking the devices

In the VSCode status bar, the default device will be displayed. If we click on it, we can choose the device (for example, Linux, Chrome, or an emulated Android device).

### Step 3. Launching our application

To run our application, we use the **Run** button in the top-right corner of VSCode. This will run the application on the selected device.

## Managing Flutter Projects from the Command Line

A more versatile way to create projects with Flutter is to invoke the `flutter create` command directly from the command line.

To do this, the most basic form will be:

```
$ flutter create <directory>
```

This will generate a Flutter project in the specified folder. If that folder doesn't exist, it will be created automatically. We can also generate it in the current folder with `flutter create .`.

> **About folder names**
>
> The name of the folder where we save a Dart (and therefore Flutter) project must be specified in snake_case format, consisting only of lowercase letters and numbers, separated by underscores. With this convention we ensure compatibility between file systems that don't distinguish between uppercase and lowercase, and we improve readability with underscores in file and folder names.

By default, when we create a project with Flutter, a folder is generated inside it with the projects for each platform we have configured (android, web, ios, linux, etc.)

If we want to generate the project only for certain specific platforms, we can do so with the `--platforms` option. For example:

```
$ flutter create --platforms android,web app_exemple
```

Additionally, if we already have a project created, we can use this same command to add new platforms, without having to recreate the project. For example, if in the previous project we wanted to add the linux platform, we could do:

```
$ flutter create --platforms linux app_exemple
```

On certain occasions, such as when we create an Android project for a specific SDK version and open it in a different one, the project may have build problems.

A solution to this would be to delete the `android` folder and regenerate it with `flutter create --platforms android .`

## Managing Devices from the Command Line

To see the connected devices, we use the command:

```
$ flutter devices
```

Which will show us output like the following:

```
Found 2 connected devices:
  Linux (desktop) • linux  • linux-x64      • KDE neon User Edition 6.14.0-29-generic
  Chrome (web)    • chrome • web-javascript • Google Chrome 140.0.7339.127

Run "flutter emulators" to list and start any available device emulators.
```

As we can see, it indicates that we have two connected devices: Linux, which is the machine we're on, and the Chrome browser.

If we had, for example, a physical Android device, connected to the computer and configured, it would also appear here.

> **But... where are the emulators?**
>
> As the previous output indicates, to see the emulators we have on the system we'll run:
>
> ```
> $ flutter emulators
> ```
>
> Which will return output with the list of emulated devices, similar to this:
>
> ```
> 1 available emulator:
>
> Id                  • Name                • Manufacturer • Platform
>
> Medium_Phone_API_35 • Medium Phone API 35 • Generic      • android
>
> To run an emulator, run 'flutter emulators --launch <emulator id>'.
> To create a new emulator, run 'flutter emulators --create [--name xyz]'.
> ```
>
> As we can see, it shows us the emulator with identifier `Medium_Phone_API_35`, which is the one Android generated at installation time. If we had more emulators created, they would also appear here.
>
> As indicated, to open the emulator we'll need to run:
>
> ```
> $ flutter emulators --launch Medium_Phone_API_35
> ```

> **More options**
>
> The `flutter emulators` command, in addition to `--launch`, supports other parameters that may be useful to us, such as:
>
> `--create`, to create a new emulator based on a Pixel device. This can be accompanied by the `--name` parameter to specify the device name:
>
> ```
> $ flutter emulators --create --name Nou_Dispositiu
> Emulator 'Nou_Dispositiu' created successfully.
> ```
>
> `--cold`, used with `--launch`, allows us to perform a cold boot of the device (as if we turned it on again). If we don't specify anything, generally, when we close the emulator it saves its state, and it's restored when we start it. With `--cold` what we do is ignore this saved device state.

## Running the Application from the Command Line

Finally, to run the application from the command line, we just need to be in the project folder and run:

```
flutter run
```

In this case, if we have an Android device or emulator, the application will be built and run on it. Otherwise, we'll be allowed to choose between the different systems on which we can launch the application (Web, Linux, Windows).

> **The first Android build**
>
> The first time we build and launch an application for Android, a large number of tasks are performed, including downloading various Gradle dependencies (Android's project format), the full build into native code, generating the APK, etc., which makes the process quite costly.
>
> In subsequent builds, it will no longer be necessary to download all the dependencies and only the modified files will be compiled, so execution will be faster.

Finally we'll see the application running on our device.

### JIT and AOT Compilation

With `flutter run` we do a JIT (Just-In-Time) build, so that it runs on the Dart virtual machine. This means we'll have Hot Reload enabled and the changes we make to the code can be seen directly in the application.

As we can see, this output is divided into three blocks:

- A first block showing information about the project build in debug mode,
- A second block, with information about various commands to interact with the running project. The ones we'll use most will be the first two:
  - **r**, to do a Hot Reload of the application. This will be very useful when we make aesthetic changes to the current screen that don't require loading information or other views,

> **The Debug label**
>
> When we have the application running with JIT, the **Debug** label appears in the top-right corner. Further on we'll see how to hide this label, even though we're in debug mode.

### Launching Releases: AOT

On the other hand, we can do an AOT (Ahead-Of-Time) build so that execution is faster without debugging possibilities, running the application in release mode:

```
flutter run --release
```

As well as generating the distribution package (APK file) for distribution with:

```
flutter build apk --release
```

In both cases, we'll have an AOT build, and even though it's not explicitly hidden, the Debug label will no longer be shown in the top-left corner.

## Modifying the Example and Live Viewing

To see how Hot Reload works, let's make some modifications to the application code.

To do this, we'll follow these steps:

**Step 1.** We open the project with VSCode, if we haven't already.
**Step 2.** We run the application with `flutter run`, preferably on the configured Android device, either from any terminal, or from the terminal integrated with VSCode.
**Step 3.** Without closing the application or the terminal from which we launched the command, we look for the `main.dart` file inside the `lib` folder and open it in the editor.
**Step 4.** We look for and replace some text strings, for example:

On line 33, we have:

```dart
// main.dart
home: const MyHomePage(title: 'Flutter Demo Home Page'),
```

Which we can replace with (being careful to escape the apostrophe!):

```dart
home: const MyHomePage(title: 'Exemple d\'aplicació amb Flutter'),
```

And on line 107, the text:

```dart
'You have pushed the button this many times:',
```

We can change it to:

```dart
'Has fet tap al botó el següent nombre de vegades:',
```

**Step 5.** Let's also try changing the application's theme. We go to line 31, where it says:

```dart
colorScheme: ColorScheme.fromSeed(seedColor: Colors.deepPurple),
```

Which indicates that the seed for establishing the color scheme is purple (`Colors.deepPurple`), and we delete the `.deepPurple` color. Now we type a dot (`.`) so that the editor shows us the different possible options for `Colors`:

And we select any one, for example, here we chose `AmberAccent`:

```dart
colorScheme: ColorScheme.fromSeed(seedColor: Colors.amberAccent),
```

Once the changes have been made and saved, and having checked that no error is marked in the code, we go to the terminal from which we launched `flutter run`, and press the **r** key to do a Hot Reload, and we'll see how the changes are applied without needing to rebuild and reload the application. Also, if we had previously pressed the "+" button, we'll see that the application keeps the state it had. This is exactly what the **Stateful Hot Reload** feature consists of.

If we run the application directly from VSCode with the **Start Debugging** or **Run without debugging** options, simply making the changes and saving the file triggers a Hot Reload, so the changes are applied immediately. Additionally, this also allows us to launch the debugging tools integrated into VSCode, instead of opening them in a web browser.

## Managing Flutter Versions with FVM (Flutter Version Manager)

FVM is a command-line tool that allows managing multiple versions of Flutter on the same machine, without any conflict between them. This ensures that each project uses the version of Flutter it needs, which is very useful when working on different projects that need specific SDK versions, when working as a team on the same application and needing to use the same version, or when we want to try new versions without affecting existing projects.

FVM works as a version manager, similar to `nvm` for Node.js or `rbenv` for Ruby.

### Installing FVM

FVM is distributed as a Dart package and can be installed globally with `dart pub global`. The most common way is:

```
dart pub global activate fvm
```

Once installed, we can check the version with:

```
fvm --version
```

### Basic Use of FVM

To see the Flutter SDK versions we have installed, we'll run:

```
$ fvm list
Cache directory:  /home/joamuran/fvm/versions
Directory Size: 0 B

No SDKs have been installed yet. Flutter SDKs
installed outside of fvm will not be displayed.
```

As we can see, initially, we don't have any Flutter version managed by FVM. As the messages tell us, SDKs we have installed outside of FVM are not shown.

### Installing a Specific Version of Flutter

To install a specific version of the Flutter SDK with fvm, what we'll need to do is:

```
fvm install <version>
```

For example, for version 3.38.7:

```
fvm install 3.38.7 --setup
```

This will download and install the specified version in the versions directory managed by FVM.

Now, we can already check the list of versions managed by FVM:

```
$ fvm list
Cache directory:  /home/joamuran/fvm/versions
Directory Size: 796.47 MB

┌─────────┬─────────┬─────────────────┬──────────────┬──────────────┬────────┬───────┐
│ Version │ Channel │ Flutter Version │ Dart Version │ Release Date │ Global │ Local │
├─────────┼─────────┼─────────────────┼──────────────┼──────────────┼────────┼───────┤
│ 3.38.7  │ stable  │ 3.38.7          │ 3.10.7       │ Jan 14, 2026 │        │       │
└─────────┴─────────┴─────────────────┴──────────────┴──────────────┴────────┴───────┘
```

### Assigning a Version to a Project

After installing the desired version, we can make a specific project use that version:

```
cd <project_directory>
fvm use 3.38.7
```

This will create a `.fvm/fvm_config.json` file inside the project, indicating which version should be used. This way, when other developers open this project with FVM, the same version will be installed and used.

To see which version is being used in a specific project:

```
fvm flutter --version
```

And with:

```
fvm doctor
```

We can see more detailed information about the execution environment and the project configuration.

### Running Flutter with FVM

When a project is configured with FVM, we can invoke Flutter through FVM:

```
fvm flutter run             # To run the application in debug mode
fvm flutter build apk       # To generate the APK
```

This ensures that the Flutter version assigned to the project is being used, regardless of the system's global version.
