In this section, we are going to address one of the most complex and, at the same time, interesting aspects of the Dart language: asynchronous programming. Complex because it involves a change in the traditional conception of concurrent programming, based on threads, and interesting because it plays a fundamental role in Flutter's reactive programming.

# Asynchronous Programming in Dart

Asynchronism refers to a programming model in which certain operations can return control of execution to the program that invoked them before they have finished.

Programming languages offer different types of mechanisms for dealing with this kind of programming, such as threads in Java or coroutines in Kotlin, among many others.

## Future

Dart and Flutter make use of the *Future* class and *async/await* to work with functions asynchronously.

*Futures* define data types associated with asynchronous tasks, which are not resolved immediately. A fairly common example of this type of task consists of requests that we make to a server. We know that they will receive a response at some point, but we do not know when.

To see an example that simulates an asynchronous function, we will define the following:

```dart
Future<String> asynchronousFunction(){
 return Future.delayed(Duration(seconds: 1), (){
   print("We are in asynchronousFunction");
   return 'Return value';
 });
}
```

This function returns an object of type *Future* after one second, which will contain a *String*. Or, more precisely, it returns an object of type *Future*, which after one second will execute a function that returns a *String*.

To simulate the pause, we have used the `delayed` method of the `Future` class. This method receives an object of type `Duration` as its first argument, and a callback function, without arguments, as its second. Notice that a `return` is also performed inside this callback function.

**The** **`Duration`** **class**

The [`Duration`](https://api.dart.dev/stable/2.18.5/dart-core/Duration-class.html) class represents a duration, or in other words, the difference between two points in time. To create an object of type `Duration`, we use its constructor, to which we can provide different named arguments (`hours`, `minutes`, `seconds`...). In the example, a duration of one second has been specified, using the `seconds` argument.

Let's see how it works with the following program:

```dart
void main(){
  print("Start");
  var a=asynchronousFunction(); 
  print(a);
  print("End");
}
```

The result displayed on screen will be:

```text
Start
Instance of '_Future<String>'
End
We are in asynchronousFunction
```

As expected, the first thing displayed is the text *Start*, corresponding to the first `print` in the program. Then, the asynchronous function is invoked and the result it returns is displayed: `Instance of '_Future<String>'`. That is, an object of type `Future`, which will contain a *String* *in the future*.

To actually obtain the value, we have to wait for it to be *resolved*, using the `then` method of the `Future` class:

```dart
Future<String> a=asynchronousFunction(); 

a.then( ( String data ) {
  print(data);
} );
```

This `then` method will be invoked when the asynchronous function returns the value, and it will now receive a piece of data of type `String` containing the function's result. It is commonly said that the variable `a` is *resolved* at this point.

If we add this to the example:

```dart
void main(){
  print("Start");

  Future<String> a=asynchronousFunction(); 

  print(a);

  a.then( ( String data ) {
    print(data);
  } );

  print("End");
}
```

We will see that the output is:

```text
Start
Instance of '_Future<String>'
End
We are in asynchronousFunction
Return value
```

As we can see, the program's execution continued normally, and the function was executed and resolved asynchronously, but now we have access to the result.

**Note**

If you come from the world of web programming, you will have noticed that Dart *Futures* are a mechanism very similar to JavaScript *Promises*.

On the other hand, if you are familiar with the `java.util.concurrent` library, it also provides a `Future` class with similar behaviour.

## Async/Await

When we want an asynchronous function to have synchronous behaviour, we can use the `await` keyword. In this way, when an asynchronous function is invoked, we are telling Dart to wait for it to finish instead of continuing execution.

This would be written as follows:

```dart
String a = await asynchronousFunction();
print(a);
```

In this way, during the same invocation, we would wait for the asynchronous function to finish (making it synchronous), and, most importantly, **we would receive the** **`String`** **returned by the function directly, instead of the** **`Future`** **that we received before**.

In addition, when we use an `await` inside a function (including the `main` function), it must be declared as `async`, as follows:

```dart
void main() async {
  print("Start");

  String a=await asynchronousFunction(); 
  print(a);

  print("End");
}
```

With this, the result will now be the expected one for synchronous behaviour:

```text
Start
We are in asynchronousFunction
Return value
End
```

### Future.wait

The static `Future.wait` method allows us to perform several asynchronous operations simultaneously, grouping them into a list of `Futures` (`List<Future<T>>`). `Future.wait` waits until all the `Futures` in the list are completed, and returns a Future containing a list of the results (`List<T>`) in the same order, or an error if any of them fails.

In this way, we reduce the total execution time because the tasks are executed in parallel, and the resulting code is cleaner and more efficient.

**Parallelism with JavaScript**

If a `Future` would be the equivalent of a JavaScript `Promise`, the `Future.wait` method would be the equivalent of JavaScript's `Promise.all`.

On the other hand, the equivalent of saying that a Promise is *resolved* in JavaScript would be to say that a Future is *completed* in Dart.

Let's see an example:

```dart
Future<void> main() async {
  // Define three asynchronous tasks that complete after different durations
  Future<String> future1 = Future.delayed(
    Duration(seconds: 2),
    () => 'Result 1',
  );
  Future<String> future2 = Future.delayed(
    Duration(seconds: 1),
    () => 'Result 2',
  );
  Future<String> future3 = Future.delayed(
    Duration(seconds: 3),
    () => 'Result 3',
  );

  print('Starting Future.wait...');
  // Wait for all the tasks to complete
  final results = await Future.wait([future1, future2, future3]);
  print('All tasks have completed');

  // the results are in the same order as the original Futures
  print('Results: $results');
}
```

**Note**

Notice that in the previous example, the result is obtained when all three Futures have completed, and the results are obtained in the same order in which the call was made. This is independent of when the different Futures complete.

Let's make a variation of the previous example, printing when each result is returned by the *Future* (notice that now, because we add more than one statement to the callback function, we no longer express it as an arrow function, but instead use braces and the `return` keyword):

```dart
Future<void> main() async {
  // Define three asynchronous tasks that complete after different durations
  Future<String> future1 = Future.delayed(Duration(seconds: 2), () {
    print("Returning result 1");
    return 'Result 1';
  });
  Future<String> future2 = Future.delayed(Duration(seconds: 1), () {
    print("Returning result 2");
    return 'Result 2';
  });
  Future<String> future3 = Future.delayed(Duration(seconds: 3), () {
    print("Returning result 3");
    return 'Result 3';
  });

  print('Starting Future.wait...');
  // Wait for all the tasks to complete
  final results = await Future.wait([future1, future2, future3]);
  print('All tasks have completed');

  // the results are in the same order as the original Futures
  print('Results: $results');
}
```

Now the output will show how the Futures are completed, in the order established by the timers, but the output of `wait` keeps the results ordered according to the invocation order.

```text
  Starting Future.wait...
  Returning result 2
  Returning result 1
  Returning result 3
  All tasks have completed
  Results: [Result 1, Result 2, Result 3]
```

## Behind Asynchronism in Dart: The Event Loop

When we start a Dart application (and, by extension, a Flutter application), a new process is created, or an *Isolate* in Dart terminology. This thread is unique, meaning that operations are performed one after another. Furthermore, while an operation is being performed, it will not be interrupted by another process.

In this context, we need to ask ourselves how Dart manages concurrency, bearing in mind that when we work with Flutter we find ourselves in an environment that is completely event-driven.

The answer lies in the Event Loop, the Dart code sequencer.

When we create a Dart process or *Isolate*, the following operations are performed:

1. Two FIFO queues are initialised: *MicroTask* and *Event*, which will store tasks to be performed with different priorities.
2. The `main()` method is executed.
3. Once `main` has finished, the Event Loop is launched, which will execute the tasks in the queues in an orderly manner.

The operation of this Event Loop is shown in the following flowchart:

[Source: https://dart.cn/articles/archive/event-loop](https://joamuran.net/flutter2026/u2/img/eventLoop.png)

Basically, the Dart process does not finish while there are pending tasks in any of the queues.

The main difference between the two queues is priority, since the microtask queue has precedence over the event queue. This microtask queue is usually used for very short internal actions that must be executed asynchronously after a certain operation has finished, and before control is returned to the event loop. On the other hand, events are launched when the microtask queue is empty and there are pending events.

Generally, we will work with events, such as reading a file, receiving the response to a network request, or reading from a database.

Let's look at the following example, where two tasks will be generated: one will be a timer event (`Future.delayed`), which is triggered after 0 ms, and the other will be a microtask scheduled using the `scheduleMicrotask` function from the `async` library:

```dart
import 'dart:async';

void main() {
  print("Start");
  Future.delayed(
      Duration(milliseconds: 0), 
      () => print("Hello from the event queue")
  );

  scheduleMicrotask(
      () => print("Hello from the microtask queue")
  );

  print("End");

}
```

The result is:

```text
Start
End
Hello from the microtask queue
Hello from the event queue
```

# Streams

*Streams* were introduced by the Flutter team at Google I/O 2018, and they constitute the main component of reactive programming in Flutter.

When we talk about reactive programming, we refer to the propagation of changes in the application's state in order to maintain its consistency. Thus, the application *reacts* to changes as they occur, avoiding the need to perform state updates manually.

A *Stream* consists of a sequence of asynchronous events, which can be defined in one place and to which information can be added and read from other places.

A fairly common analogy in the documentation is that of a conveyor belt. Imagine that we have a belt that *transports* objects from one end to the other. There is an entity that adds elements to the belt, and after an indeterminate amount of time, these objects are at the other end of the belt. Two things can then happen: either there is someone ready to *capture* these objects from the belt, or they *fall* and end up being lost if nobody picks them up.

To define a Stream, we need a generic type indicating the type of data that this Stream will *transport*:

```dart
Stream<GenericType> my_stream;
```

## Initial Example

Let's first look at a small example of how to create a Stream from an object of type *Future*.

We have the following function, which uses `Future.delayed` to return a *Future* that, after 5 seconds, will resolve to a String containing the current time:

```dart
Future<String> getTime() async {
  // Returns a string after 5 seconds
  print("[Info] Starting getTime function");
  await Future.delayed(Duration(seconds: 2));

  print("[Info] Two seconds have passed. Now adding data");
  var time = DateTime.now();
  return "${time.hour}:${time.minute}:${time.second}";
}
```

As we can see, we use `await` and `async` to wait for the pause to finish before returning the data.

With this, we define the `main` function as follows:

```dart
void main() {
  print("[Info] Starting main");

  // Create a Stream containing a String from a Future
  Stream<String> stream = new Stream.fromFuture(getTime());

  print("[Info] The stream has been created");

  // Capture the Stream data
  stream.listen((data) {
    print("Current time: " + data);
  }, onDone: () {
    print("Task completed");
  }, onError: (error) {
    print("An error occurred");
  });

  print("[Info] End");
}
```

In the code we can observe the following:

* We have defined the stream using a generic type of *String*. Therefore, the objects it will *transport* will be of this type, which is exactly the data type to which the *Future* obtained from the `getTime` function resolves.
* To prepare to receive data in the Stream, we have used the *listen()* method, which we will discuss in more detail later.

The result of executing this program is:

```text
[Info] Starting main
[Info] Starting getTime function
[Info] The stream has been created
[Info] End
[Info] Two seconds have passed. Now adding data
Current time: 6:58:59
Task completed
```

As we can see, the result is as expected, and by using `async` and `await`, everything works synchronously.

## The listen Method

The `listen()` method is defined as follows:

```dart
StreamSubscription<GenericType> listen(
  void Function(GenericType)? onData, 
  {
    Function? onError,
    void Function()? onDone,
    bool? cancelOnError, 
  }
)
```

As we can see, it returns an object of type *StreamSubscription*, which, as its name indicates, represents a subscription to the events of the *Stream*. This subscription provides us with several methods for managing events (`onData`, `onError` and `onDone`), and can also be used to cancel the subscription or temporarily pause it.

With this, the `listen` method can receive up to four arguments:

* The first (`onData`) is the only *mandatory positional* argument, and consists of a callback function that will be invoked whenever data is received by the *stream* (that is, when the *StreamSubscription* triggers the *onData* event). It is also commonly said that the *stream* has emitted data at this point. This callback receives as an argument the data that has been added to the Stream (`(data){...}`).
* The *optional named* argument `onError`, which consists of a callback function that will be triggered when an error occurs in the *Stream* (the *onError* event of the *StreamSubscription*). This callback will receive a description of the error (`onError: (error){...}`), or the error code and a stack trace (`onError: (error, StackTrace){...}`). If we do not detect possible errors here, they will have to be handled at higher levels of the code.
* The *optional named* argument `onDone`, which is also a callback and will be invoked when the stream is closed (the `StreamSubscription` triggers the *onDone* event).
* The *optional named* argument `cancelOnError` is a Boolean value which, if set to true, automatically cancels the subscription when the first error event is received. By default, its value is false.

As we can also see in the definition above, all these arguments are defined as *nullable*. If these parameters are set to null, no error will occur, but the event will be *consumed* and no action will be performed.

When we cancel or pause a subscription, we will not receive any of these events, so none of these handlers will be invoked.

While a subscription is paused or has been cancelled, the subscription does not receive events and none of the event-handler functions are called.

On the other hand, it should be taken into account that most Dart Streams are single-subscription streams, which means that once an event has been *consumed*, it cannot be *consumed* again, and an exception would be thrown if we attempted to do so.

### Ways of Providing Callbacks

The callback functions that we can provide to the `listen` method can be specified in several ways, either by using anonymous/lambda functions, arrow functions, or functions defined beforehand. Let's look at some examples where we define the callback for the `onData` event so that, when it occurs, it simply writes the received data to the screen:

* **Example 1:** Using a lambda function (in this case, we could specify more than one action):

```dart
listen((item) { print(item); }); 
```

* **Example 2:** Using an arrow function (we could only specify one action):

```dart
stream.listen((data) => print(data)); 
```

* **Example 3:** Using a previously defined function:

```dart
void myPrint(String message) {
  print(message); 
} 

stream.listen(myPrint);
```

**Note**

If you have knowledge of other environments such as .NET or Kotlin, Streams would be the equivalent of *Observables* in .NET or *LiveData* in Kotlin.

## StreamController

The most common way of working with *streams* will be through the *StreamController* class, which, as its name indicates, is a *controller* associated with a *stream*. This class will be used to create *streams* for other entities to listen to, and will allow us to add events and data to them.

To create a *stream* using a *StreamController*, we would write:

```dart
var controller = new StreamController<GenericType>();
```

As we can see, the StreamController uses a generic type, which defines the type of object that we can add to the *stream*.

To add data to this *stream*, we can use the `add` method of the controller itself:

```dart
controller.add(ObjectOfGenericType);
```

For example, to define a *stream* that *transports* Strings and add information to it, we would write:

Ex:

```dart
StreamController controller = new StreamController<String>();
controller.add("My text");
```

**Important**

The `StreamController` class is defined in Dart's *async* library, and therefore, to use it we need to import this library:

```dart
import 'dart:async';
```

Now, to add an event listener (*listener*) to the *stream* associated with the controller, we would write:

```dart
controller.stream.listen((item) { /* Event handler */ }); 
```

An example of what we have just seen would be the following:

```dart
import 'dart:async';

void main(List<String> args) {
  StreamController controller = new StreamController<String>();

  controller.stream.listen((item) => print(item),
      onError: (error) => print("The following error occurred: $error"),
      onDone: () => print("The stream has been closed"));

  print("Adding item1");
  controller.add("Item1");
  print("Adding item2");
  controller.add("Item2");
  print("Adding item3");
  controller.add("Item3");
}
```

As you can see, the *listener* is defined first, and information is then added to the *stream*. If we run the previous program, we will see that the output is:

```text
Adding item1
Adding item2
Adding item3
Item1
Item2
Item3
```

As we can see, the items are added in a certain order and are intercepted by the *listener* in the same order. In other words, a *stream*, as we would expect if we compare it with the conveyor-belt analogy, has a FIFO (*First-In-First-Out*) structure.

### Cancelling Subscriptions

To cancel a subscription to a *Stream*, we use the `cancel` method of the `StreamSubscription` returned by the `listen` method:

```dart
StreamSubscription subscription =
      controller.stream.listen(...);
...
subscription.cancel();
```

Let's see it with the previous example:

Example:

```dart
import 'dart:async';

void main(List<String> args) async {
  StreamController controller = new StreamController<String>();

  // Store the subscription
  StreamSubscription subscription = controller.stream.listen(
      (item) => print(item),
      onError: (error) => print("The following error occurred: $error"),
      onDone: () => print("The stream has been closed"));

  print("Adding item1");
  controller.add("Item1");
  print("Adding item2");
  controller.add("Item2");

  subscription.cancel();
  // Cancel the subscription

  print("Adding item3");
  controller.add("Item3");
}
```

What would the result of the previous example be? Would we see *Item1* and *Item2* being captured, but not item 3?

If we run it as we have it, the result will be:

```text
Adding item1
Adding item2
Adding item3
```

As can be seen, all three items have been added, but the cancellation occurred before we were able to *capture* any object. Using the conveyor-belt analogy, we would have stopped waiting for objects before the first one reached the end of the belt.

However, if we make a small pause before the cancellation:

```dart
import 'dart:async';

void main(List<String> args) async {
  StreamController controller = new StreamController<String>();

  // Store the subscription
  StreamSubscription subscription = controller.stream.listen(
      (item) => print(item),
      onError: (error) => print("The following error occurred: $error"),
      onDone: () => print("The stream has been closed"));

  print("Adding item1");
  controller.add("Item1");
  print("Adding item2");
  controller.add("Item2");

  // Pause
  await Future.delayed(Duration(milliseconds: 100));

  // Cancel the subscription
  subscription.cancel();

  print("Adding item3");
  controller.add("Item3");
}
```

We would then obtain:

```text
Adding item1
Adding item2
Item1
Item2
Adding item3
```

As we can see, we get to listen to the *Item1* and *Item2* objects, but we cancel the subscription before item 3 arrives.

### Adding Errors

To throw an error on a *Stream*, we use the controller's `addError` method. For example:

```dart
import 'dart:async';

void main(List<String> args) async {
  StreamController controller = new StreamController<String>();

  // Store the subscription
  controller.stream.listen((item) => print(item),
      onError: (error) => print("The following error occurred: $error"),
      onDone: () => print("The stream has been closed"));

  print("Adding item1");
  controller.add("Item1");
  controller.addError("Error 400");
  print("Adding item2");
  controller.add("Item2");
}
```

In this case, the output would be:

```text
Adding item1
Adding item2
Item1
The following error occurred: Error 400
Item2
```

### Closing the Stream

Finally, to close the Stream, we use the `close` method of the *StreamController*. Once it has been closed, no more elements can be added to the Stream.

For example, the following code:

```dart
import 'dart:async';

void main(List<String> args) async {
  StreamController controller = new StreamController<String>();

  // Store the subscription
  controller.stream.listen((item) => print(item),
      onError: (error) => print("The following error occurred: $error"),
      onDone: () => print("The stream has been closed"));

  print("Adding item1");
  controller.add("Item1");

  // Close the Stream
  controller.close();

  print("Adding item2");
  controller.add("Item2");
}
```

In this case, it will throw the exception:

```text
Unhandled exception:
Bad state: Cannot add event after closing
```

To handle this, we can use a *try-catch* block:

```dart
try {
  print("Adding item1");
  controller.add("Item1");
  controller.close();
  print("Adding item2");
  controller.add("Item2");
} catch (e) {
  print("Exception caught: $e");
}
```

Or we can use the Controller's `isClosed` method to check beforehand whether it is closed:

```dart
print("Adding item1");
controller.add("Item1");
controller.close();
print("Adding item2");
if (!controller.isClosed) controller.add("Item2");
```
